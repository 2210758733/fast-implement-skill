# fast-implement（编码直达省流）

编码落地任务按此规则执行，目标是：**改动更快、消耗更少、别让单会话 context 越滚越大**。
只在用户要你「开工写/改代码」时触发；纯问答、纯调研不适用。

省流的真实大头是下面三条结构性机制，其余是配套纪律：
1. 不重读已在上下文里的文件、不整仓扫描；
2. 廉价探查拆给轻模型子代理，强模型留作综合与决策；
3. 大任务/长会话优先新代理/新会话 + 压缩中间产物，而不是堆进一个 context。

预期省流中等但真实，先出一版能用，之后按实测迭代，不吹嘘上限。

## 一、直达实现（快）

- 只读完成本次改动「必需」的最小文件集。已在本会话读过的文件**不要再读**；定位用定向 Grep/Glob，不做全仓/全目录扫描。
- 一次一小步：读必要内容 → 直接写代码/改文件 → 跑该步最窄的检查。**实现先于文案**：不先输出大段规划、不做开场寒暄、不贴无关上下文。
- 独立的工具调用尽量**并行**发出（并行 Read、并行 Bash），减少串行往返。
- 需要环境事实时，做低成本定向查找（只看该函数/该文件头/该调用点），不整文件、不整仓库读。
- 验证：只跑被改动处最窄的检查（单测/运行一次）；除非用户明确要，不扫全量测试套件、不做多余的交叉核对。

## 二、隐藏推理减负

- 探查类工作（找文件、摸清一片接口/代码、搜集背景）尽量**拆给子代理**跑，主线程等其结论再综合决策。子代理 prompt 必须自包含、写明确切文件路径与「输出范围」（如：只回结论，≤200 字），避免它扩散上下文。
- 拆探查给轻模型子代理（`model: lite`），把强模型留给写关键代码/做架构决策。子代理返回的是压缩过的结论，不进大段原始日志。
- 不要让子代理做「理解后替我实现」这种模糊活——它没看过本会话；只给它明确定位的窄任务。

## 三、会话卫生（内置）

- 任务偏大时：宁可起「窄上下文新子代理」分步做，也别把中间产物/长日志/大 diff 全灌进主 context。
- 中间产物过长（超长日志、大段输出）：先压缩成关键结论再继续，必要时只保留到磁盘文件而不是贴进对话。
- 会话明显膨胀（约 >200KB 或单任务做了很久、堆了很多工具调用）：主动停下来，建议「写交接文档 + 开新会话」继续，而不是硬撑着累积。开新会话时把已定事实/文件路径/下一步写清楚再交接。

## 四、输出纪律

- 中文，**结论 + 关键数字先行**，不铺陈、不寒暄、不复述用户的话。
- 只保留高信号内容；改动说明尽量短，让用户扫一眼能看懂「做了什么 / 改了哪个文件 / 结果如何」。
- 收尾按当前工作空间已有的交接/记忆约定落地（若适用），不额外造一套。
